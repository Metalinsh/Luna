# 1. 问题与场景

用户在早期为了方便存储与搬运，把大量专辑与音声作品以**独立压缩包**形式保存（一个作品一个 `.zip` / `.7z` / `.rar`，常含 10–60 GB 的无损音频）。这些内容对 Luna 完全不可见：既不进专辑墙，也不能检索、播放。

**已有的兜底建议是「全部解压」**，但它在当前场景下代价过高：

| 代价 | 说明 |
| --- | --- |
| 磁盘 | 音声无损包解压后体积几乎翻倍，1 TB 归档会膨胀到约 2 TB |
| 时间 | 一次性解压上千个包是数小时级的纯等待 |
| 反复 | 用户一旦重新打包，之前的整理成果（标签、封面、收藏）与路径绑定就断了 |
| 不可逆 | 解压后的目录结构往往比原包更乱，回不去 |

因此本文档给出一个**不需要解压**的替代路径。

---

# 2. 设计立场

> **不劝用户解压，也不假装压缩包不存在。**
> 把压缩包变成 Luna 的一个**只读虚拟音乐库**：包内成员成为可浏览、可检索、可播放的一等公民；
> 只有用户明确要求时，内容才落到磁盘上——且落盘是一次**可预览、可撤销、默认不删除源包**的搬运。

这与 Luna 既有的设计原则同源（音声元数据只存库内、任何修改用户文件的操作都必须先预览影响面）：

- **压缩包永远只读**：Luna 不写、不改、不重命名任何包；
- **源包是权威副本**：落盘产物是派生数据，删掉可以随时重新生成；
- **新引入的唯一破坏性操作（删源包）默认关闭**，且必须二次确认。

---

# 3. 关键前提：音频包与视频包的收益天差地别

压缩包里的内容不同，价值完全不同。这是本设计里最该讲清楚的一点：

| 包内容 | 压缩收益 | 按需解码代价 | 结论 |
| --- | --- | --- | --- |
| WAV / AIFF / 整轨镜像 | **极高**（约 50–65%，无损压到 1/2） | 低（流式 DEFLATE 可边解边喂） | ✅ 最值得保留归档态 |
| FLAC / ALAC / APE | 低（2–8%） | 中 | ⚠️ 归档仅为打包方便 |
| **MP3 / AAC / MP4** | **极低（≤2%）** | **高**（压缩后彻底失去随机访问） | ❌ **建议落盘，不再打包** |

**产品结论**：界面对 MP3/MP4 为主的包给出「建议落盘」提示，而不是让用户为了省 2% 磁盘、付出每次播放都全量解包的代价。

> P1 实测样本（`[RJ123218] … .zip`，620 MB）：54 个 mp3 + 1 张 jpg，压缩率仅约 0.8%。
> 该样本完美印证「已压缩格式没必要归档」这条结论——它更适合作为落盘（P3）的验证对象。

# 4. 三个核心抽象

现有实现有三处硬前提：`tracks.path` 是磁盘真实路径、`/api/stream/:id` 用 `fs.createReadStream` 打开真实文件、`music-metadata` 从真实文件读标签。
本设计**不推翻**这些前提，而是在其下插入两层薄抽象。

## 4.1 字节范围读取器 `openReader(src)`

```
openReader(src) -> {
  size()                             // 不解压即可知大小
  read(rangeStart, rangeEnd)         // 按需解出指定字节（P2）
  stream(range)                      // 供 /api/stream 直接管道（P2）
  materialize(destPath, onProgress)  // 落盘，带 CRC 校验（P3）
  close()
}
```

后端实现按能力逐级降级，**绝不假装**：

| 包类型 | 读取方式 | 随机访问 |
| --- | --- | --- |
| 目录（现状） | 直接 fs | ✅ 完整 |
| ZIP（stored，method=0） | 中央目录 + 直接偏移 | ✅ 完整，range 几乎零成本 |
| ZIP（deflate，method=8） | 中央目录 + 流式 inflate | ⚠️ 需缓存 |
| 7z / RAR / ISO / 分卷 | 7-Zip CLI 定向抽单成员 | ⚠️ 需缓存 |
| CUE + 整轨 | 偏移表换算 + range | ✅ 完整 |

**P1 范围**：只做 ZIP（stored + deflate），其余格式登记为「暂不支持」并如实上报，不静默跳过。

## 4.2 虚拟路径

```
<压缩包绝对路径>\u0000<包内成员相对路径（正斜杠）>
```

**为什么用这个格式**：`server/asmr.mjs` 的路径解析全是纯函数（`locateRelease` 按 `[\\/]` 切段找 RJ 号、`resolveVersion` 看目录链、`titleFromFolder` 剥 RJ 前缀）。
把虚拟路径拼成「**压缩包文件路径 = 一个虚拟目录**」，则：

- `locateRelease()` 自然把**压缩包文件本身**识别为发行根 → 每包一张卡；
- RJ 号从包文件名 `[RJ123218] ….zip` 中取到，标题即包名；
- 包内的版本目录（实测：`バイノーラル編集　効果音あり/` 与 `…効果音なし/`）自然成为**版本**；
- 差分标注、特典分离、`おまけ` 折叠、格式优先级**全部自动成立，asmr.mjs 无需改动业务逻辑**。

这是本方案能低成本落地的根本原因。

`tracks` 表新增 `source_kind ∈ {file, archive_member}`；虚拟路径存进原有的 `path` 列（`UNIQUE` 约束天然生效）。

## 4.3 资源状态机（必须对用户可见）

```
归档态 ──播放（P2）──▶ 缓存态 ──用户确认（P3）──▶ 落盘态
（零解压）              （.lam-cache/ 可删）        （音乐库目录，真实文件）
```

界面必须区分这三态并显示占用，不允许出现「我没解压，怎么占了 20 G」。

- **P1**：全部曲目处于**归档态**。`materialized_state = 'archived'`。
- **P2**：引入缓存态与 `.lam-cache/`。
- **P3**：引入落盘态，路径重指向，走既有 `write-jobs.mjs` 安全框架。

# 5. P1 实现规格（只读包清单入库）

**目标**：用户把压缩包放进已登记的音乐库，扫描后**立刻**在专辑墙上看到它们——封面、版本角标、音声三层轨道模型全部正确，且**全程零解压写入**。

## 5.1 ZIP 解析（`server/zip-reader.mjs`）

只读中央目录，不解压任何音频数据。

| 能力 | 做法 |
| --- | --- |
| 定位目录 | 从尾部 64 KB 内倒序找 EOCD（`0x06054b50`） |
| ZIP64 | EOCD64 定位器（`0x07064b50`）→ EOCD64（`0x06064b50`），仅取条目数 |
| 遍历条目 | 中央目录记录 `0x02014b50`，逐条读 flags / method / CRC / 尺寸 / 本地头偏移 / 名称 |
| 解压 | `stored` 直接读；`deflate` 用内置 `node:zlib`（`inflateRawSync` / 流式 `createInflateRaw`） |
| 暂不支持 | method 除 0/8 外（bzip2 / LZMA / deflate64 / zstd）→ 该成员标 `unsupported` |
| 加密 | flags bit0 → 该成员标 `encrypted`，P1 不解 |
| 损坏 | 尾部有本地文件头但无有效 EOCD → 判定「不是压缩包」，当作普通文件放行，不报错 |

### 5.1.1 文件名编码（本设计最易踩坑处）

ZIP 规范只在 flags bit11 置位时保证名称为 UTF-8。**实测样本恰恰没有置位**（63 个条目全部 `utf8FlagSet=0`），名称是 **Shift-JIS**：

```
原始字节（latin1 视角）      正确解码
¥Ð¥¤¥Î©`¥é¥ë¾É¡¡...    →   バイノーラル編集　効果音あり
```

**策略（按优先级）**：

1. flags bit11 置位 → 按 UTF-8 解；
2. 未置位 → 用 `TextDecoder` 依次尝试 **UTF-8（fatal）/ Shift-JIS / GB18030**，按「替换字符 U+FFFD 与私用区字符更少」打分取胜者；
3. 记录 `archive_members.name_encoding`，供界面提示与排障；
4. 已知局限：GB18030 与 Shift-JIS 对纯假名/常用汉字序列解码结果相同（实测样本上二者逐字节一致），此时任选其一都不影响可读性。

> 依据：`TextDecoder` 的 `shift_jis` / `gb18030` 在 Node 24 内置可用（已实测），**无需新增依赖**。

### 5.1.2 封面挑选

复用音声规则 R13 的优先级思路，在**包内路径**上判断：`高画质封面 / 封面 / package / cover / artwork` 命中优先，其次按自然序、最后按体积取最大。命中后解出该成员 → 交给既有 `persistCoverImage()` 内容寻址存储。

## 5.2 数据模型（schema v6）

```sql
CREATE TABLE archives (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  library_id INTEGER, path TEXT NOT NULL UNIQUE,
  format TEXT NOT NULL DEFAULT 'zip',
  entry_count INTEGER NOT NULL DEFAULT 0,
  audio_count INTEGER NOT NULL DEFAULT 0,
  image_count INTEGER NOT NULL DEFAULT 0,
  packed_bytes INTEGER NOT NULL DEFAULT 0,
  unpacked_bytes INTEGER NOT NULL DEFAULT 0,
  encrypted INTEGER NOT NULL DEFAULT 0, header_encrypted INTEGER NOT NULL DEFAULT 0,
  unsupported INTEGER NOT NULL DEFAULT 0,
  name_encoding TEXT,
  status TEXT NOT NULL DEFAULT 'ready',   -- ready | partial | error | unsupported
  error TEXT, scanned_at INTEGER, created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL
);

CREATE TABLE archive_members (
  archive_id INTEGER NOT NULL, member_path TEXT NOT NULL,
  size INTEGER, packed_size INTEGER, method INTEGER, crc32 INTEGER, mtime INTEGER,
  kind TEXT, name_encoding TEXT,
  PRIMARY KEY (archive_id, member_path)
);

-- tracks 新增列
ALTER TABLE tracks ADD COLUMN source_kind TEXT NOT NULL DEFAULT 'file';
ALTER TABLE tracks ADD COLUMN archive_id INTEGER;
ALTER TABLE tracks ADD COLUMN member_path TEXT;
ALTER TABLE tracks ADD COLUMN materialized_state TEXT NOT NULL DEFAULT 'ready';
```

- `source_kind='archive_member'` 且 `materialized_state='archived'` 表示「在包内，尚未落盘」；
- 登记 `archive_members` 的意义：**增量扫描时比对清单**，包内成员变化即可精确增删，无需重新遍历；同时为 P2 的按需取成员提供偏移索引。

## 5.3 扫描接入（`server/scanner.mjs`）

1. `walkAudioFiles()` 顺带收集压缩包（扩展名 `.zip`，先做轻量签名探测：文件尾 64 KB 内含 EOCD 才认）；
2. `ingestArchive(archivePath, libraryId)`：
   - `probeZip()` 列清单 → `store.upsertArchive()` + 写入 `archive_members`；
   - 合成虚拟文件列表（`{path, name, ext, size, kind}`，`path` 为虚拟路径）；
   - 把该列表交给 `analyzeRelease(root, { files })` —— **asmr.mjs 只需把内部 `walkFiles(root)` 换成可注入的参数**，其余逻辑零改动；
   - 复用 `ingestRelease()` 的写库流程（版本 / 轨道 / 自动 ASMR 标签 / 封面）；
3. **P1 不读包内标签**：`analyzeRelease` 的 `readTags` 传 `false`，曲目标题由文件名推导（音声的 `displayTitleOf` 本来就负责这件事），因此 P1 完全不需要解压音频数据；
4. 封面是 P1 唯一需要解压的对象（通常 0.5–5 MB，可接受）；
5. 清理阶段：包已消失或成员已不在清单中的曲目，按既有 `seen` 机制删除；
6. `scanState` 增加 `archivesParsed / archiveEntries / archiveTracks / archivesUnsupported` 等计数，随 `persistLastScan()` 落库。

## 5.4 播放保护（P2 前的诚实降级）

P1 不做流播，因此 `/api/stream/:id` 必须**明确拒绝**归档态曲目，而不是抛 500 或静默无效：

```
HTTP 409 { error: '该曲目位于压缩包内，P2 版本将支持直接播放', code: 'ARCHIVE_NOT_MATERIALIZED' }
```

前端在曲目行上把播放按钮置为「包内」禁用态并给出提示，符合「静默失败是不允许的」这条既有承诺。

## 5.5 界面

- **专辑卡片**：新增 🗜 角标（音声角标行），显示该发行来自压缩包；
- **专辑详情 / 曲目表**：归档态曲目显示「包内」标记；
- **侧栏统计**：新增「压缩包」条目（包数 / 包内曲目数 / 原包体积 / 解压后体积）；
- **压缩包视图**（P1 简版）：列出所有已登记包的状态与计数，便于排障。

## 5.6 P1 验收标准

| # | 标准 | 验证方式 |
| --- | --- | --- |
| 1 | 指向压缩包所在音乐库扫描后，专辑墙出现对应卡片，封面非空 | 真机（`E:\Music\ASMR` 测试包） |
| 2 | 音声三层模型正确：版本数 = 包内版本目录数，轨道按轨号合并，特典进折叠组 | 对比包内目录结构 |
| 3 | **扫描期间不写入、不修改任何用户文件**，源包 mtime/大小不变 | 扫描前后核对 SHA-1 与 mtime |
| 4 | 包内成员数量、总体积与包清单一致（`archive_members` 计数核对） | 单元测试 + 真机 |
| 5 | Shift-JIS 文件名正确解码为可读日文，编码判定被记录 | 单元测试断言具体字符串 |
| 6 | 损坏 / 不支持格式的包被如实计数并出现在扫描报告的 `errors` 中，不阻塞其余扫描 | 单元测试 + 真机 |
| 7 | 删除包后重扫，其曲目与（无其它曲目的）专辑卡片被清理 | 真机 |
| 8 | 既有 V1.0 功能与 117 条单元测试全绿，`schema_version` 迁移到 6 且不丢数据 | `pnpm test:full` |

# 6. 边界情况

| 情况 | 处理 | 阶段 |
| --- | --- | --- |
| 加密包（音声分流常见） | 弹密码框 → 内存中试解 → 可选「记住该包密码」，默认**不保存**；header 加密时连清单都读不到，标 `need_password` | P4 |
| 分卷（`.part1.rar` / `.z01` / `.001`） | 按首卷归一为一条记录，缺卷标 `partial` 并列出缺失卷名 | P4 |
| 包内嵌套包 | 默认只展开一层，标「内嵌压缩包」不递归，防递归炸弹 | P4 |
| 包损坏 | 标 `damaged`，**其余包照常扫描** | P1（已含降级） |
| 递归炸弹 | 限制单成员解压上限与解压比（>500:1 拒绝） | P2 |
| 路径长度 / 非法字符 | 落盘时按 Windows 规则清洗，记录「原名 → 新名」映射 | P3 |
| 网络盘 / 移动硬盘 | 首卷不可达 → 标离线，界面显示「源包不可达」而非报错 | P2 |
| CUE + 整轨镜像 | 按偏移表切成虚拟轨道，**切片不落盘** | P4 |

# 8. 技术选型与许可证

| 需求 | 选择 | 理由 |
| --- | --- | --- |
| ZIP 解析 / deflate | **自研 + `node:zlib`** | 内置模块，**零新增运行时依赖**（守住现有「仅 3 个依赖、无原生编译」底线） |
| 文件名编码 | **内置 `TextDecoder`** | `shift_jis` / `gb18030` 均已实测可用 |
| tar / gz / xz / zstd（P4） | 系统自带 `bsdtar`（libarchive 3.8.8，已实测存在） | 零依赖，BSD 许可 |
| 7z / RAR / ISO（P4） | `7zip-bin`（MIT 包）或探测本机 7-Zip | **7-Zip 含 unRAR 限制条款，正式分发前需法务确认** |
| 明确不引入 | 任何原生编译模块（`@node-rs/*` 等） | 会破坏「无原生编译、可打包」这条现有底线 |

# 9. 性能目标

- 1 万个包内条目的**首次清单扫描** ≤ 30 秒，且期间**不解压任何音频数据**；
- 单包（≤1000 成员）清单解析 ≤ 1 秒；
- 扫描内存增量与包内条目数成线性、与包体积**无关**（只读中央目录）；
- P2 追加：包内 WAV 首播延迟 ≤ 2 秒，已缓存成员切轨 ≤ 300 ms。

# 11. 与既有设计的关系

| 既有规则 | 本设计的衔接 |
| --- | --- |
| 音声专辑 R1–R15（三层模型） | 虚拟路径直接复用，业务规则零改动 |
| 「音声元数据只存库内，绝不写回」 | 压缩包只读，天然一致；P1 连标签都不读 |
| 写操作五道关口（`write-jobs.mjs`） | P3 的落盘任务直接接入，白捡备份 / 乐观锁 / 校验 / 撤销 |
| 封面内容寻址存储 | 包内封面解出后复用同一条流水线 |
| 「静默失败是不允许的」 | 不支持 / 加密 / 损坏的包必须出现在扫描报告与界面上 |
| 用户资产不可重建 | 包内曲目的标签、收藏、社团、艺术家决策照常存库，与包路径解耦于虚拟路径 |

# 12. P1 实测结论（真机验证）

验证对象：`E:\Music\ASMR\[RJ123218] エッチで弟大好きなお義姉ちゃんの性教育～最高にあまあまな早漏訓練編～ 【伊ヶ崎綾香】.zip`
（**620 MB**、63 条目 = 6 目录 + 54 mp3 + 1 jpg + 2 txt、全部 deflate、**UTF-8 标志位全部未置位**）

## 12.1 达成情况

| 指标 | 目标 | 实测 | 结论 |
| --- | --- | --- | --- |
| 清单解析 | ≤ 1 秒 | **9 ms**（63 条目） | ✅ 远超目标 |
| 扫描入库（含封面解出） | — | **约 400 ms** | ✅ |
| 压缩包解析耗时 | — | **3–4 ms**（不计封面） | ✅ |
| 流式读单个成员（20 MB mp3） | — | **99 ms** | ✅ 为 P2 铺路 |
| 解压正确性 | 逐字节一致 | **zlib.crc32 与包内 CRC32 完全相符** | ✅ |
| 源包安全 | 绝不修改 | 扫描前后 **SHA-1 + 大小 + mtime 完全一致** | ✅ |
| 入库结果 | 一层不差 | 54 条曲目 / 7 个版本 / 封面落地 | ✅ |
| 既有测试 | 全绿 | **117 / 117** | ✅ |

## 12.2 P1 期间发现并修复的四个真实缺陷

这些都是**真实包才暴露**的问题，合成测试包不会触发：

| # | 缺陷 | 根因 | 处置 |
| --- | --- | --- | --- |
| 1 | `path.relative()` 对虚拟路径返回 `'..'` | Windows 上路径解析遇到 NUL 分隔符即失败，导致三层模型整体退化为「无版本」 | 改为纯字符串前缀裁剪（`relOf`），并统一 `/` 分隔 |
| 2 | 发行根多出一截 | `locateRelease()` 未在 NUL 处先分段，把包名与包内第一层目录粘成一段，专辑键与 `rootDir` 不一致，曲目挂不上专辑 | 新增 `pathLayers()` 两级分段，重组时原样写回 NUL |
| 3 | 包根成员落进名为「ASMR」的假版本 | `relOf` 剥前缀时只认 `\` 与 `/`，不认 NUL；整个绝对路径泄漏成目录链 | 前缀边界接受三种分隔符 |
| 4 | 同轨差分副本被算成额外版本 | 版本名取了目录链最后一段（如作品名重复包装层） | 新增 `stripWrapperSegments()` 只从开头连续剥离包装段，并过滤 `<包名>.zip` 自身 |

顺带修正：`pickCover()` 原要求 `kind === 'other'`，但图片本身的 kind 是 `image`，导致**包内封面永远选不中**。

## 12.3 声明的已知局限

1. **`使用例` 单列为一个版本**（2 条轨）。它们是「訓練失敗 差分のみパート」下与主版本同轨道的差分副本，
   理想应合并展示。属既有 `resolveVersion` 的多层目录语义，非本次引入，不影响播放/检索/收藏。
2. **编码判定在 Shift-JIS 与 GB18030 之间不可区分**：纯假名与常用汉字序列在两种编码下解码结果**逐字节相同**，
   因此界面可能显示 `gb18030` 而文件实际是 Shift-JIS。对可读性无影响（设计文档 §5.1.1）。
3. **包内曲目暂不能播放**：`/api/stream` 尚未对归档态做 409 诚实降级（P1 收尾项，见 §7 的 P2）。

# 13. P2 实测结论（按需解码与预读取）

验证对象同 §12（620 MB、54 个 mp3）。缓存目录用临时位置，避免污染开发实例。

## 13.1 实现落点

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 缓存登记 | `db.mjs` schema **v7** `cache_entries` | 成员 → 缓存文件映射、`last_used_at`（LRU 依据） |
| 解码引擎 | `collection.mjs` `ensureMemberCached()` | 容量判定 → 流式落盘 → 原子改名 → 登记 |
| 容量判定 | `collection.mjs` `canCacheMember()` | 单成员超上限 / 磁盘不足 → **明确拒绝并给原因** |
| LRU | `collection.mjs` `evictCache()` | 按 `last_used_at` 回收到上限的 90%，**排除正在播放的成员** |
| 供流 | `index.mjs` `/api/stream/:id` | 归档成员先确保已缓存，再对缓存文件做真正的 Range 流 |
| 预读取 | `index.mjs` `/api/archive/prefetch` | 单曲或整张，逐条返回结果与原因 |
| 缓存管理 | `/api/archive/cache`、`/api/archive/cache/clear` | 状态 / 一键清空（清空同时清登记表） |
| 交互 | `app.js` 预读取询问框 + 进度浮层 | 询问单曲/整张/暂不 → 解码 → 播放 |

**缓存目录默认值**：`<应用根>/luna_cache`（`config.mjs` 的 `APP_ROOT`；便携模式跟随 exe）。
可在设置界面改成任意绝对路径。

## 13.2 达成情况

| 指标 | 目标 | 实测 | 结论 |
| --- | --- | --- | --- |
| 单成员解码（1.3 MB） | 首播 ≤ 2 秒 | **14–16 ms** | ✅ 远超目标 |
| 整张解码（54 条 / 0.61 GB） | — | **2.8–2.9 秒** | ✅ |
| 已缓存成员再取流 | 切轨 ≤ 300 ms | **命中缓存，不再解码** | ✅ |
| 解码吞吐 | — | 约 **90 MB/s** | ✅ |
| 解压正确性 | 逐字节一致 | 解出体积与清单完全一致，Range 请求返回正确字节数 | ✅ |
| 超过上限的成员 | 放弃并提示 | 返回 `MEMBER_TOO_LARGE`，提示写明体积与解决方向 | ✅ |
| LRU 回收 | 降到上限以内 | 3 个成员降到上限 90% 以内，磁盘文件同步删除 | ✅ |
| 缓存可重建 | 删了能重建 | 被回收的成员可重新解码 | ✅ |
| 源包安全 | 绝不修改 | 扫描/解码前后 SHA-1 与 mtime 一致，库内无 `.lam-undo` | ✅ |
| 既有测试 | 全绿 | 12 区域 / 15 检查项全部通过（单元 149 + 界面断言） | ✅ |

## 13.3 P2 期间发现并修复的缺陷

| # | 缺陷 | 根因 | 处置 |
| --- | --- | --- | --- |
| 1 | 背景透明度只让设置抽屉变透明，主界面没变 | `--bg-elev` 被一并改成透明，而主内容区 `.main` 原本**没有自己的背景**（只继承 body，被抽屉盖住） | 拆成两层：`--bg-surface`（主内容区/侧栏/播放条，受透明度影响）与 `--bg-elev`（卡片/面板/抽屉，始终不透明）；并给 `.main` 显式设背景 |
| 2 | 自定义背景图不显示 | 图挂在 `body` 上，但 `.app` 的各种不透明底把它盖住了 | 改为 `.app::before` 铺图 + 主内容区透明透出 |
| 3 | 点击曲目只说"需预读取"却不执行 | 当时只有 P1 的诚实降级，没有解码链路 | 本阶段实现完整链路：询问 → 解码 → 播放 |
| 4 | `canCacheMember` 抛 `fmtBytes is not defined` | 清理死代码 `cachePathFor` 时误删了 `fmtBytes` | 恢复定义（已被容量判定测试覆盖） |
| 5 | 启动时未取缓存额度，询问框不显示"已用" | `loadCacheStatus()` 只在打开设置时调用 | 启动时一并加载 |
| 6 | 整张预读取后点下一首又弹询问 | 详情页数据是进页面时那份，`needs_prefetch` 仍为 true | 整张成功后 `openAlbum(id, { push: false })` **就地重新加载** |
| 7 | 顶部搜索条不跟随背景/透明度 | `.topbar` 写死 `rgba(11,11,15,.86)` | 改用 `var(--bg-surface)`，与主内容区同层 |
| 8 | 浅色模式下播放条与搜索框仍是黑的 | 写死深色底（`rgba(16,16,22,.94)` / `--bg-elev`） | 新增 `--overlay-rgb`（深色叠深、浅色叠白）供覆盖式半透明面板使用 |
| 9 | 浅色模式下大量白色叠加看不见 | 42 处 `rgba(255,255,255,…)` 硬编码 | 统一改为 `rgba(var(--mix-fg),…)`；封面渐变/占位/阴影也改为变量 |

## 13.4 声明的已知局限

1. **LRU 只有上限，没有时间维度**：不按"多久没用"过期，只按容量回收。
2. **整张预读取是串行等待**：54 条 2.8 秒可以接受，但更大的专辑会让询问框的进度浮层停留更久；
   期间界面可继续操作（浮层不阻塞），但该次播放要等解码完成。
3. **混编码包的少数派条目**仍可能解错（§12.3 第 2 条），与 P2 无关。
4. **`--autoplay-policy`**：界面自检脚本必须带此参数，否则脚本点击不算用户手势、播放会被浏览器拦下（测试环境问题，不是产品问题）。
5. **透明度拉到 0 时文字会压在背景图上**：此时底色全透，对比度由背景图决定，不是配色能解决的；
   浅色模式 / 深色模式只负责在**有底色**时保证可读。建议配浅色背景图时用浅色模式 + 透明度 ≥ 60%。

## 13.5 外观设置（深/浅色、配色、透明度、背景图）

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 深浅模式 | `dark` / `light` | 翻转底色与文字色，并翻转 42 处叠加色与原生控件 `color-scheme` |
| 配色方案 | `midnight` / `nebula` / `graphite` | 强调色与色底；浅色模式下各自有对应浅色变体 |
| 背景透明度 | 0–100 | 只作用于**大块面**（主内容区 / 侧栏 / 顶部条 / 播放条）；卡片、面板、抽屉始终不透明 |
| 背景图 | 任意绝对路径或 data URL | 铺在 `.app::before`；有图时侧栏与播放条改用覆盖式半透明底 |
