## 0.5.2 音声（ASMR）专辑能力

音声作品多为「一个发行 = 多个版本 × 多条轨道」的目录结构，通用音乐模型无法表达，因此引入**三层轨道模型**（发行 → 版本 → 轨道），完整规则见 [`音声专辑设计.md`](音声专辑设计.md)。V1.0.0 已实现：

- **RJ 号识别**：文件夹名中的 `[RJxxxxxxxx]` 作为检索键与发行标识
- **版本识别**：`本篇 / 无音效 / 无饮尿 / 无音效、无饮尿` 等，**以文件夹名为准**，标签仅作交叉校验，冲突时提示人工确认
- **差分标注**：同一版本下多个文件按其括号内标记区分（如 `无音效 无饮尿`），避免出现两个同名按钮
- **轨道合并**：按轨号把多版本合并为一行，行内以按钮切换版本；相似文件名自动合并，不确定的交给人工确认
- **格式优先级**：每个版本内 **wav 优先于 mp3**，视频文件作为独立「视频版」按钮
- **特典分离**：`おまけ / 特典` 轨道进入可折叠分组；`alarm` 等噪声文件忽略
- **封面优先级**：高画质封面图 > `package/artwork` > 其它图片
- **自动打标**：入库时自动打上 `ASMR` 标签
- **不写回**：音声发行的标题、艺术家、社团**全部只存库内**，绝不修改用户文件

## 0.5.4 艺术家决策机制（防错设计）

**问题**：某音声的 mp3 标签里 `albumartist` 写着厂牌名（`plug in.東京`），而所有曲目的 `artist` 都是声优名（`逢坂成美`）。直接采用 `albumartist` 会把错误信息显示在专辑墙上。

**规则**：

1. **以曲目 `artist` 标签为准**（音声作品里它最贴近实际演出者）
2. `albumartist` 与之明显不同时**不采用**，降级为「标签建议」并在详情页提示
3. 提示提供两个按钮：**采用它**（改为标签值，仅影响软件显示）与 **保持现状**（维持 artist 值）
4. 任一选择后提示消失，`artist_decision` 记入库，**重新扫描不再重复询问**
5. 手工填写的艺术家标记为 `manual`，**永不被扫描覆盖**

**连带能力**：填写社团/艺术家时，自动套用到**文件夹名或标题中包含该文字**的其它音声发行，避免重复劳动；
并同时为这个名称**建立同名标签**，打到「本次填写的 + 被套用的」全部作品上（社团与艺术家对称，单张填写、
批量填写、采用标签建议三条路径都会触发）。已经填着同一名称的作品**只打标签、不重写字段**，
以免把它的来源从 `tag` 强改成 `manual` 而冻结后续扫描。

## 0.5.5 界面要点

- **专辑墙**：卡片显示封面、专辑名、`[社团] · 艺术家` 署名行、版本数/特典/视频版角标、ASMR 标签；
  上方标签栏按 **风格 / 社团 / CV** 三栏展示，点标签即筛选（AND/OR 由顶部下拉决定）
- **专辑详情**：封面 + 元信息 + 曲目表；曲目表右侧三个操作按钮（喜欢/歌词/在资源管理器显示）**常亮且右端对齐**，标题/艺术家/时长**列宽可拖动**且不与按钮重叠；**双击曲目名播放**；
  **点封面看完整原图**（走「看原图」浮层）；曲目表下方是**图片预览**栏目（按图片所在文件夹分组，点缩略图看原图）
- **包内发行**：详情页多出**预读专辑 / 清除缓存**两个按钮（仅当该专辑有包内曲目时出现），
  各带确认框；整张预读全部成功 → 自动打「已预读」标签（归入「风格」栏）；清除缓存只清该专辑的成员缓存，
  并撤下它的「已预读」标签
- **单曲详情**：左侧封面占**窗口一半宽度且可拖动**（20%–70%），下方大字标题，再下方 `艺术家：X  社团：Y`；右侧歌词（带 **A+ / A−** 字号调节）；底部**复用主界面同一条播放组件**（同一 DOM 节点，非复制体）
- **播放组件常驻**：启动即完整显示，不留黑条
- **音量 0–200%**：`HTMLMediaElement.volume` 规范上限是 1.0（= 数字满刻度），所以 100% 以上另接一层
  **Web Audio 增益**（`createMediaElementSource → GainNode → DynamicsCompressor 软限幅 → destination`）实现软件放大。
  两个刻意的取舍：① **懒接入** —— 只有用到 >100% 才创建音频图，≤100% 走的仍是原来的元素音量，不引入
  「AudioContext 被自动播放策略挂起 → 静音」的风险；建图**只发生在用户手势里**（启动时读到 >100% 先按 100% 播，
  首次点击/按键再补上）。② **接上就一路走 gain** —— 元素音量固定 1.0，音量全由 gain 决定，避免两处叠加。
  100% 刻度画在滑轨中点，进入放大区时数值与图标转为警示色
- **播放模式**：列表循环 → 顺序播放 → 单曲循环 → 随机播放（顺序播放在最后一首结束后停止）

# 0. 本次修订摘要（先读这一节）

## 0.1 场景发生了什么变化

| 维度 | V1.0（旧场景） | V2.0（新场景） |
| --- | --- | --- |
| 用户状态 | 音乐已整理好，只想"看"和"听" | 音乐**已在固定目录，但数量大、未分类**，需要**整理** |
| 产品定位 | 只读浏览器 | **分类管理 + 元数据维护工具** |
| 与文件的关系 | 绝不修改音频文件 | **支持修改并写回音频文件**（用户明确要求） |
| 组织维度 | 专辑自动聚合（标签驱动） | 聚合 + **用户自定义多标签**（人工分类） |
| 数据完善 | 缺失就兜底显示"未知专辑" | **主动提醒缺失 + 引导用户补全** |
| 播放 | 播放/暂停/上下首 | 增加**三种播放模式**与**滚动歌词** |
| 数据库地位 | 纯缓存，可随时删除重建 | **包含不可重建的用户资产**（标签、库别名、手动归并） |
| 风险等级 | 极低（只读） | **高**（写文件）→ 必须建立写操作安全框架 |

## 0.1.1 已确认的场景参数与推论（rev.2 新增）

**确认结论**

| 项 | 确认值 | 对设计的影响 |
| --- | --- | --- |
| 「重命名音乐库」的含义 | **仅改软件内显示名（别名）**，不涉及任何路径或文件改动 | 物理目录重命名**移出范围**；删除了原设计的目录改名流程、`library-rename` 写任务类型与对应 API；少了一条高风险写路径 |
| 音乐库规模 | **1 TB 以上，5000 首以上** | 平均 **≈ 200 MB / 首** → 判定为 **Hi-Res / DSD 为主的库** |

**由规模参数推出的五个设计结论**

| # | 推论 | 依据 | 受影响章节 |
| --- | --- | --- | --- |
| 1 | **瓶颈是"单文件体积"，不是"记录条数"**。5000 条记录对 SQLite 与前端渲染毫无压力 → **FTS5 全文索引与虚拟滚动均非必需**，可推迟 | 5000 曲目 ≈ 500 张专辑，`LIKE` 查询在毫秒级 | 5.6.3、10.2 |
| 2 | **写回代价 = 文件体积 × 文件数**，一次"全量复制备份 + 全量复制工作副本"要产生数 GB I/O → 备份必须改为**同卷 rename（零拷贝）** | 一张 10 首的专辑 ≈ 2 GB | 5.3.3 |
| 3 | **Hi-Res 资源常内嵌 3000px 大封面（5–10 MB）**，500 张专辑一次性加载会撑爆浏览器内存 → **必须生成缩略图** | 500 × 8 MB ≈ 4 GB | 5.4.5 |
| 4 | Hi-Res 库中 **DSD（.dsf/.dff）、APE、WavPack 占比可能很高**，而这类格式**既不能写回、浏览器也不能播放** → `db-override` 降级与**播放代理**从边缘路径变为主流路径 | 附录 A 矩阵 | 5.3.7、5.8.4 |
| 5 | 1 TB 音乐库通常位于**外置硬盘 / NAS / 机械盘** → 需要处理掉盘、慢速盘、网络盘，且**备份必须与源文件同卷** | 跨卷 rename 会退化为整文件复制 | 5.3.3、8.3 |

> ⚠️ **连带风险**：推论 4 意味着，如果您的库里 DSD 占比很高，则"浏览器内播放"这条需求（R5）在当前技术栈下**只能通过服务端转码实现**。这已写入 5.8.4，并在第 11 章作为待确认问题（Q11）。请优先确认您库中 **DSD / FLAC / WAV / ALAC 的大致比例**。

## 0.2 场景变更引出的三个架构决定

### 决定 1｜专辑必须实体化，使用稳定 ID（不能再用派生键当身份）

V1 用**派生键** `album_key = 专辑艺术家 + 专辑名` 作为专辑身份，且没有 `albums` 表。

一旦支持编辑元数据，这个设计立刻崩溃：用户把专辑名从 `未命名专辑` 改成 `OK Computer`，`album_key` 就变了——**挂在该专辑上的标签、封面、待完善状态会全部失联**。

**方案**：新增 `albums` 表，`albums.id` 为稳定主键；`tracks.album_id` 外键关联；`album_key` 降级为"聚合计算依据"，可随元数据变化而更新（含合并逻辑，见 5.3）。

### 决定 2｜引入写操作安全框架（第五章 5.3 详述）

写文件是本产品**唯一不可逆的风险来源**。所有写操作统一走五道关口：

```
预览影响面 → 自动备份 → 原子替换 → 写后校验 → 可一键撤销
```

任何绕过该框架的写路径都视为设计缺陷。

### 决定 3｜"索引可删可重建"不再成立，用户资产必须可导出

V1 可以放心地说"删掉 `data/` 重扫即可"。V2 不行：**标签、库别名、手动归并关系、待完善状态**都是用户手工输入的成果，删了就没了。

**方案**：新增 `GET /api/backup/export` 与导入功能，可一键导出用户资产为 JSON；并在界面上明确区分"可重建的索引数据"与"不可重建的用户数据"。

## 0.3 安全承诺修订（重要）

> **V1 承诺**：绝不修改用户的音频文件。
>
> **V2 承诺**：**绝不静默修改用户的音频文件。**

每一次写入都必须满足：

| 关口 | 要求 |
| --- | --- |
| ① 用户显式触发 | 不存在任何"自动整理""自动修复"式的后台写入；写操作必须由用户点击并确认 |
| ② 影响面预览 | 执行前列出"将修改 N 个文件 / 涉及 M 张专辑"的清单 |
| ③ 强制备份 | 每次都把原文件复制到 `data/undo/<jobId>/`，不提供"跳过备份"选项 |
| ④ 原子替换 | 先写临时文件、校验通过后再原子替换；中途失败原文件完好无损 |
| ⑤ 可撤销 | 每个写任务登记在 `write_jobs` 表，支持一键回滚到操作前状态 |

# 1. 产品概述

## 1.1 一句话定义

**把已经堆在固定目录里、数量庞大且没有分类的专辑，变成一个有标签、有封面、元数据完整、可检索、可播放并带滚动歌词的可视化专辑墙——并且所有对信息的修改都能安全地写回音乐文件本身。**

## 1.2 使用场景（用户原话转述）

> 用户已在本地建立固定存放专辑的目录，但专辑文件太多且未分类，管理不便，需要可视化界面对专辑进行分类管理。

拆解为六个必须满足的能力：

| # | 需求 | 本质 |
| --- | --- | --- |
| R1 | 手动添加音乐库路径，并重命名音乐库 | **库的组织** |
| R2 | 读取专辑文件信息（封面/艺术家/曲名）；缺失时提醒并支持手动完善；**修改同步写回文件** | **信息完善（含写回）** |
| R3 | 为专辑添加复数标签（摇滚/纯音乐/日系流行…），并可按标签检索 | **人工分类** |
| R4 | 识别已有歌词文件，播放界面滚动展示歌词 | **歌词体验** |
| R5 | 播放模式：列表循环、单曲循环、随机播放 | **播放控制** |
| R6 | 已收录专辑形成可视化专辑墙 | **可视化总览** |

## 1.3 目标用户

**核心画像｜"收藏很多但很乱"的整理型用户**
本地有 500～20000 首音乐，按大致目录堆放，标签质量参差：有的专辑完整规范，有的只剩文件名。他会主动花时间整理，愿意补封面、改标签、打分类——**但极度在意"别把我的文件搞坏"**。

**次要画像｜按风格听歌的用户**
不需要按专辑听，而是想"来点纯音乐""放点日系流行"。对他而言**标签就是导航**，专辑墙是入口，播放模式是刚需。

## 1.4 产品定位的变化

| | V1.0 | V2.0 |
| --- | --- | --- |
| 一句话 | 看和听 | **整理、分类、补全、再看再听** |
| 核心动词 | browse / play | **organize / tag / complete / verify** |
| 成功标准 | 打开能看到专辑墙 | **打开能看到"待完善 N 张"，处理完后库变得整齐可用** |
| 信任基础 | 不碰文件 | **碰文件，但每一步都可预览、可回退** |

## 1.5 设计原则（修订版）

| 原则 | 含义 | 落地要求 |
| --- | --- | --- |
| **⚠️ 永不静默写入**（替代原"只读安全"） | 写操作必须显式、可见、可撤销 | 五道关口（0.2 决定 2） |
| **文件是唯一事实来源** | 索引可重建，且**写入后必须重新解析文件**而非信任内存 | 写后强制 reparse 校验 |
| **用户资产与索引分离** | 明确区分"可重建"与"不可重建"数据 | 导出/导入接口 + 界面提示 |
| **先提醒，后操作** | 不自动修复，只提示缺失，由用户决定怎么补 | 待完善工作台 |
| **分类以标签为主，目录为辅** | 用户不该为了分类去挪文件 | 多标签 + 标签检索 |
| **本地优先** | 不联网、不登录、不上传；宁可让用户手填也不偷偷抓取 | 无外部请求 |
| **渐进增强** | 标签缺失、歌词缺失、封面缺失都不能让功能不可用 | 四级兜底策略沿用 V1 |

## 1.6 非目标（V2 明确不做）

- ❌ 联网抓取元数据 / 封面（MusicBrainz、AcoustID、豆瓣等）—— 保持本地优先；如未来要做，必须单独设计授权流程
- ❌ 自动批量整理（"一键修复全部"）—— 与"永不静默写入"冲突
- ❌ 移动文件 / 删除文件：可编辑标签、可重命名库的**显示名**，但**不移动、不重命名、不删除**任何音频文件或目录
- ❌ **物理重命名音乐库目录**（已由需求方确认：重命名仅指软件内显示名）—— 理由：这是纯收益为零、风险却很高的操作；用户若有需要，直接在资源管理器里改名后重新扫描即可
- ❌ 多用户、账号、云同步
- ❌ CD 抓轨、CUE 分轨
- ❌ 移动端适配（窄屏布局仍未实现）
- ❌ 音频转码 / 格式转换

## 1.7 术语表

| 术语 | 含义 |
| --- | --- |
| **音乐库（Library）** | 用户登记的根目录；有**别名**（显示名）与**物理路径**两个概念 |
| **专辑实体（Album）** | `albums` 表中的一行，有稳定 `id`；标签、封面、待完善状态都挂在它上面 |
| **聚合键（album_key）** | 由"专辑艺术家 + 专辑名"派生的计算值，用于把新增曲目归入已有专辑；**不再是身份** |
| **音轨标签（Track Tag）** | 写在音频文件内的标准字段（ID3/Vorbis/MP4），会随文件走 |
| **应用标签（App Tag）** | 本软件自定义的多标签分类（摇滚/纯音乐…），默认只存数据库，可选同步写入文件自定义字段 |
| **写任务（Write Job）** | 一次写操作的完整记录：影响清单、备份路径、状态、回滚信息 |
| **待完善（Incomplete）** | 专辑/曲目缺失关键或建议字段的状态，由完整性规则判定 |

# 3. 用户旅程

## 3.1 首次整理（核心流程）

```
① 建库        添加音乐目录 → 弹窗可填「库别名」（如"我的 FLAC 收藏"）
                ↓
② 扫描        进度条：扫描文件 → 解析标签 → 清理失效 → 补充封面
                ↓
③ 总览        专辑墙出现，其中若干张卡片带 ⚠ 角标
              侧栏显示「待完善 37 张」
                ↓
④ 待完善工作台 按缺失类型分组：无封面 21 / 无艺术家 9 / 无音轨号 14 / 无年份 6 / 无标签 37
                ↓
⑤ 逐项处理    · 补信息：打开编辑抽屉，填艺术家/专辑/年份 → 保存 → 写回文件 + 校验
              · 补封面：选择本地图片 → 写入内嵌封面或目录 cover.jpg
              · 打标签：输入"摇滚"回车即创建并应用；或从已有标签里勾选
                ↓
⑥ 分类完成    专辑墙可筛可搜，标签一栏点"纯音乐"即筛出全部相关专辑
```

## 3.2 日常检索与播放

```
打开 → 顶栏搜索「曲名 / 艺术家」→ 结果即时过滤
     → 或点标签 chips「日系流行」「纯音乐」→ 专辑墙按标签筛选
     → 点专辑 → 播放整张 / 点单曲播放
     → 播放器切到「正在播放」→ 大封面 + 滚动歌词，当前行高亮
     → 切换播放模式：列表循环 ⇄ 单曲循环 ⇄ 随机
```

## 3.3 批量维护

```
待完善工作台 → 选中「无年份」的 6 张专辑
            → 批量填充面板：年份 1997 → 应用到 6 张
            → 预览："将修改 62 个文件" → 确认
            → 写任务卡片显示进度 → 完成后可「撤销本次」
```

## 3.4 数据安全路径

| 用户担心的 | 产品的回答 |
| --- | --- |
| 改错了怎么办 | 每次写操作生成 write job，一键撤销 |
| 写到一半断电 | 原子替换，原文件完好；写任务标记为"中断"，可重试 |
| 文件被其他程序占用 | 写入前检测，失败则跳过并汇总报告，不影响其他文件 |
| 软件出问题会不会毁库 | 备份在 `data/undo/`，即使软件崩了也能手工还原 |
| 标签会不会丢 | 导出的用户资产 JSON 包含全部标签与库配置 |

**关键交互规则**

# 5. 功能规格

## 5.1 音乐库管理（R1）

### 5.1.1 添加音乐库

沿用 V1 行为（路径归一、必须为目录、去重忽略大小写、添加后默认立即扫描），**新增**：

| 新增项 | 规格 |
| --- | --- |
| 库别名 | 可选。留空则取路径的文件夹名；最长 40 字符；允许重名（仅作显示） |
| 别名用途 | 侧栏、筛选器、统计页显示别名；技术性位置（错误信息、tooltip）始终显示真实路径 |
| 重复添加 | 返回 200 且 `added: false`，但复用已登记的别名，不覆盖用户改过的名字 |

### 5.1.2 重命名音乐库（已确认：仅指软件内显示名）

> **需求确认**：「重命名音乐库」= 在软件内更改显示的名称，**不涉及专辑文件路径与文件的修改**。因此这是零风险操作；物理目录重命名**已移出产品范围**（见 1.6 非目标）。

| 项 | 规格 |
| --- | --- |
| 入口 | 侧栏库条目 → 悬停「✎」；库管理页亦可 |
| 修改对象 | 仅 `libraries.display_name`，**不触碰文件系统** |
| 默认值 | 未设置时显示路径的文件夹名（`E:\Music` → `Music`） |
| 校验 | 非空、≤ 40 字符、去除首尾空格；允许与其他库重名 |
| 交互 | 就地编辑：回车保存 / ESC 取消；**无确认弹窗**（零风险，可随时再改） |
| 显示规则 | 侧栏与选择器显示别名；tooltip 与技术性位置（错误、扫描报告）始终显示真实路径 |
| 撤销 | 不需要撤销机制（直接再改即可），但记入操作历史备查 |

**这一确认带来的简化收益**

去掉物理目录重命名后，本产品的写操作**风险面收缩到"仅音频文件自身的标签与封面"**，不再存在"改变文件位置/路径"的高风险操作：

- `write_jobs.type` 不再需要 `library-rename` 类型；
- 不再需要"改目录名 → 批量改写全部索引路径 → 失败回滚目录名"这套脆弱的事务逻辑；
- 用户"软件会不会动我的目录结构"的疑虑彻底消除。

### 5.1.3 移除音乐库

沿用 V1：删除该库全部索引与空封面记录，**不动任何文件**。确认框写明："库内专辑的标签与编辑记录也会一并移除；音频文件与目录不受影响。"

> 若用户确实在资源管理器里挪动了音乐库目录：直接"移除"旧路径 → "添加"新路径 → 重新扫描即可。索引重建成本很低（5000 首约数分钟），无需设计路径迁移功能。

## 5.3 元数据编辑与写回（R2 后半 —— 本产品的风险核心）

### 5.3.1 写操作框架（五道关口）

所有写操作（写回标签、写内嵌封面、写目录 `cover.jpg`、保存 `.lrc`）统一走同一框架，登记为 **write job**。

```
[1] 预览  →  [2] 备份  →  [3] 原子写  →  [4] 校验  →  [5] 可撤销
     │           │            │             │            │
   影响清单   原文件副本    临时文件替换   重新解析比对   write_jobs 表
```

**写任务状态机**

```
pending → running → verifying → done
             │          │
             ├──────────┴──→ failed（原文件未改动，可重试）
             └─────────────→ interrupted（进程中断，启动时检测并提示）
                                      ↓
                                   undone（用户撤销，已从备份还原）
```

### 5.3.2 写回实现架构

| 层 | 选型 | 理由 |
| --- | --- | --- |
| **读取** | `music-metadata` 11（保留） | 已在用，解析宽容、速度快、支持内嵌封面与歌词 |
| **写入** | [`node-taglib-sharp`](https://www.npmjs.com/package/node-taglib-sharp) 6.0.3 | **纯 JS 实现（依赖仅 uuid / os-locale / iconv-lite，无原生编译）**，保住了 V1"零原生模块"的特性；统一 API 覆盖 MP3 / FLAC / M4A / OGG / Opus / WAV / AIFF / WMA / APE / AAC |
| **降级写入器** | `node-id3` 0.2.9 | 仅 MP3，作为 MP3 写失败时的备选与交叉验证 |
| **可选扩展** | `ffmetadata`（需外部 ffmpeg 二进制） | 仅用于 taglib 不支持的冷门格式；**默认关闭**，启用需用户显式配置 ffmpeg 路径 |
| **校验** | `music-metadata` 重新解析 | 用与读取完全相同的解析器校验，避免"写进去读不出来" |

> ⚠️ **许可提示**：`node-taglib-sharp` 为 **LGPL-2.1-or-later**。本地自用无影响；若未来对外分发本软件，需遵守 LGPL 的动态链接/源码提供义务（可考虑改为进程隔离调用或替换写入器）。

**适配器接口**（对内统一，屏蔽格式差异）

```js
// 伪代码：所有格式共用同一契约
interface MetadataWriter {
  supports(ext): boolean
  write(filePath, patch: {
    title?, album?, albumArtist?, artists?,
    trackNo?, discNo?, year?, genre?, composers?, comment?,
    picture?: { data: Buffer, mime: string } | null   // null 表示移除
  }): Promise<void>
}
```

### 5.3.3 原子写流程（逐文件）

| 步骤 | 操作 | 失败后果 |
| --- | --- | --- |
| 1 | **写前检查**：文件存在、`fs.access(W_OK)`、尝试以 `r+` 打开（探测占用）、扩展名可写、磁盘可用空间 ≥ 文件大小 × 2.2 | 跳过该文件并记录原因，不改动任何东西 |
| 2 | **乐观锁校验**：比对 `size + mtime` 是否为编辑开始时的值 | 若已变化 → 拒绝写入，提示"文件已被外部修改，请重新加载" |
| 3 | **备份**：`copy original → data/undo/<jobId>/<seq>.<ext>` | 备份失败 → **中止整个任务**（不允许无备份写入） |
| 4 | **工作副本**：`copy original → <同目录>/.lam-tmp-<jobId>-<seq>.<ext>` | 失败 → 中止该文件 |
| 5 | **写标签**：taglib 打开工作副本 → 赋值 → `save()` → `dispose()` | 失败 → 删除工作副本，记录原因 |
| 6 | **验证**：用 `music-metadata` 解析工作副本，逐字段比对期望值 | 不符 → 删除工作副本，报"写入校验失败" |
| 7 | **原子替换**：`fs.rename(工作副本 → 原路径)`（Windows 上 Node 使用 `MoveFileEx(MOVEFILE_REPLACE_EXISTING)`，同卷内为原子操作） | 失败（被占用等）→ 删除工作副本，原文件完好 |
| 8 | **索引同步**：重新解析原文件 → 更新 `tracks` / `albums` / 完整性状态 | 失败 → 标记"索引待刷新"，下次扫描自动修复 |
| 9 | **清理**：删除临时文件；备份按保留策略清理 | — |

**为什么用"工作副本 + rename"而不是直接让 taglib 写原文件**：taglib 的 `save()` 是就地重写，中途失败会留下损坏文件；先写副本再原子替换，可保证**任何时刻原文件要么是旧内容、要么是新内容**。

**磁盘开销**：瞬时占用 ≈ 原文件 × 2 + 备份 × 1。对单文件 > 500MB 的高解析音频，执行前额外提示。

### 5.3.4 编辑字段规格

| 字段 | 写入目标 | 校验规则 |
| --- | --- | --- |
| 曲名 | ID3 `TIT2` / Vorbis `TITLE` / MP4 `©nam` | 非空（清空时回落文件名）；≤ 200 字符 |
| 艺术家 | `TPE1` / `ARTIST` / `©ART` | ≤ 200 字符；多值以 `; ` 分隔原样保留 |
| 专辑艺术家 | `TPE2` / `ALBUMARTIST` / `aART` | ≤ 200 字符 |
| 专辑名 | `TALB` / `ALBUM` / `©alb` | 非空；≤ 200 字符 |
| 音轨号 / 碟号 | `TRCK` / `TPOS`（`n/total` 形式保留 total） | 1–999 整数 |
| 年份 | `TDRC`/`TYER` / `DATE` / `©day` | 1000–2100 整数 |
| 流派 | `TCON` / `GENRE` / `©gen` | 自由文本 ≤ 60 字符；提供历史流派与常用列表下拉 |
| 作曲家 | `TCOM` / `COMPOSER` | 可选 |
| 注释 | `COMM` / `COMMENT` | 可选 |

**空值语义（关键 UX 规则）**

| 用户操作 | 语义 | 行为 |
| --- | --- | --- |
| 字段留空未触碰 | 不修改 | 该字段不进入 patch |
| 点击字段旁的「清除」按钮 | **显式清空** | 写入空值（删除该标签帧） |

> 批量编辑时这条规则尤其重要：绝不能用"空输入框"把用户没打算改的字段清掉。

### 5.3.5 失败与冲突处理

| 错误 | 用户可见文案 | 处理 |
| --- | --- | --- |
| `EBUSY` / `EPERM`（被占用） | "文件正被其他程序使用，已跳过" | 跳过，继续下一个 |
| `EACCES`（只读/无权限） | "文件只读或无写入权限，已跳过" | 跳过 |
| `ENOSPC` | "磁盘空间不足，任务已中止" | **中止整个任务**，已完成的可撤销 |
| 格式无写入器 | "该格式暂不支持写回，仅更新数据库" | 转 `db-override`（见 5.3.7） |
| 乐观锁冲突 | "文件在编辑期间被外部修改，请重新加载" | 跳过该文件 |
| 写入校验失败 | "写入后校验不一致，已放弃该文件" | 跳过，原文件不变 |

**原则**：单个文件失败**绝不回滚已成功的文件**（避免"改了一半又回退"的更混乱状态），而是在结果面板里明确列出成功与失败清单，失败项可一键重试。

### 5.3.6 索引同步与撤销

**索引同步**：写入成功后立即用 `music-metadata` 重新解析该文件并 UPSERT，**不信任编辑表单里的值**。若重新解析出的值与期望不一致（例如写入器丢弃了某个字段），保留文件实际值并在结果中警告。

**撤销**：`POST /api/jobs/:id/undo`
- 从 `data/undo/<jobId>/` 逐个复制回原路径（同样走"工作副本 + rename"）；
- 恢复后重新解析并同步索引；
- 若原路径在此期间的目录被重命名/文件被移动 → 尽量按当前位置恢复，失败项明确列出；
- 撤销本身也是一个 write job（可再次撤销 = 重做）。

**备份保留策略**（可配置，默认）

| 维度 | 默认值 |
| --- | --- |
| 保留时长 | 30 天 |
| 总大小上限 | 5 GB（超出按时间从旧到新删除） |
| 单文件上限 | 不限制，但 > 500 MB 的文件在任务结果中标记 |

### 5.3.7 仅更新数据库的降级路径（`db-override`）

当文件无法写回（只读 / 格式不支持 / 用户选择"仅本次不写回"）时：

- 值写入数据库，该曲目/专辑标记 `meta_source = 'db-override'`；
- 界面在所有相关位置显示 **"未写回"** 标记（专辑墙角标、详情页、曲目行）；
- 明确告知后果："该信息只存在于本软件中；若文件被其他工具修改或索引重建，此覆盖会丢失。"；
- 提供"稍后写回"入口：待完善工作台内单独一栏"未写回 N 项"，修复权限/换格式后可批量重试；
- 重新解析文件时，`db-override` 字段**优先于文件值展示**，直到成功写回或用户放弃覆盖。

## 5.4 封面管理（R2）

### 5.4.1 来源与优先级

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1 | `manual` | 用户在本软件中指定/上传的封面 |
| 2 | `embedded` | 文件内嵌图片 |
| 3 | `folder` | 同目录 `cover.jpg` / `folder.jpg` / `front.jpg` 等 |

同一专辑内若不同曲目的内嵌封面不一致 → 专辑墙使用第一首的，详情页提示"各曲目封面不一致（3 种）"，并提供"统一为所选封面"操作。

### 5.4.2 添加 / 更换 / 移除

| 操作 | 流程 |
| --- | --- |
| 更换封面 | ① 选择来源：本地图片文件（文件选择框 / 拖拽）② 选择写入方式（见 5.4.3）③ 预览确认 ④ 执行写任务 |
| 多选图片 | 允许一次选多张 → 每张专辑一张（按选择顺序对应选中的专辑） |
| 移除封面 | 移除内嵌图片 + 递归项？**设计：只移除本软件记录的封面与内嵌图片，不自动删除目录里的 `cover.jpg`**（那是用户的文件，需单独确认） |

### 5.4.3 写入方式（用户选择，默认"内嵌"）

| 方式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **内嵌到音频文件**（默认） | 写入每首曲目的内嵌图片 | 走到哪都在，跨软件可见 | 体积增加（每首曲目都存一份，N 首 = N 份） |
| **写为目录 `cover.jpg`** | 在专辑目录写入/覆盖 `cover.jpg` | 一份搞定，省空间 | 拷走单个文件会丢封面 |
| 仅存数据库 | 只更新 `albums.cover_hash` | 零风险、最快 | 换电脑/重建索引即丢失（标记"未写回"） |

**内嵌方式的额外规则**：专辑内多曲目写入同一张图时，使用**同一个 Buffer** 与同一个 `hash`（内容寻址），避免重复读取文件；写入时**替换**已有内嵌图（而非追加）。

**目录 `cover.jpg` 流程**（独立于音频写流程）：若目标已存在同名文件 → 先备份原件到 `data/undo/<jobId>/` 再覆盖；同样登记 write job 支持撤销。

### 5.4.4 图片校验

| 项 | 规则 |
| --- | --- |
| 格式 | JPEG / PNG / WebP / GIF / BMP |
| 建议尺寸 | 正方形，≥ 300×300；非正方形 / 过小 → 警告但允许（不阻止用户） |
| 大小上限 | 单图 ≤ 10 MB，超过则提示并建议压缩（不自动压缩） |
| 识别 | 通过文件头魔数判断真实格式，不信任扩展名 |

## 5.5 标签系统（R3）

### 5.5.1 模型与语义

- **专辑级标签**（不做曲目级）：用户需求是"针对已有的专辑"；专辑是整理的最小单位。
- **应用标签独立于音频流派字段**：`流派(genre)` 是文件内的标准字段（古典/摇滚），`应用标签` 是本软件内的自由分类（纯音乐/日系流行/深夜循环/待重听）。两者**并存、互不覆盖、可分别检索**。
- **默认只存数据库**，不写入文件（见 5.5.6）。
- **三大分类（本轮新增）**：每个标签归属 `风格 / 社团 / CV（艺术家）` 之一，专辑墙上方按这三类**分栏**展示，
  便于直接点标签快速筛选；标签页可逐个改归类。

| 分类 | key | 来源 |
| --- | --- | --- |
| 风格 | `style` | 用户自建标签的默认去处（含「ASMR」自动标签、整张预读后的「已预读」） |
| 社团 | `circle` | 填写社团时自动建立的同名标签 |
| CV | `artist` | 填写艺术家时自动建立的同名标签 |

> 归类规则（保守，只升级不反悔）：自动标签在**新建时**写入对应分类；已有标签若还停在默认的「风格」，
> 再次填写同名社团/艺术家时会被升级；已经是社团/CV 的标签不会被改成别的类，用户的手工归类也不被覆盖。
> 老库升级到 schema v8 时按「标签名 = 库内社团名 / 音声艺术家名」做一次性归类，其余留在「风格」。
> **折叠展示**：每栏默认只占**一行**，行尾给「＋ 还有 N 个」（按实际测量：放不下的 chip 隐藏，
> 按钮自然落到第一行末尾；若按钮本身被挤到第二行，则继续让出末尾 chip 直到它也回到第一行）。
> 点它展开该栏全部标签（换行铺开，行尾给「收起」），不做横向滚动。窗口宽度变化后会重新测量。
>
> **固顶标签**：少数状态标签不跟随使用频次排序，固定排在自己那一栏的首位 ——
> 目前是「已预读」（整张预读成功后自动建立，见 `tags.mjs` 的 `LEAD_TAG_NAMES`），
> 这样用户扫一眼标签栏就知道哪些专辑已经就绪。接口用 `lead: true` 标记，排序在界面层完成。

### 5.5.2 标签操作

| 操作 | 规则 |
| --- | --- |
| 新建 | 在打标面板输入即创建（输入框建议已有标签，回车新建）；标签页可指定分类新建 |
| 命名规范 | 去首尾空格；内部连续空格归一为单个；**不区分大小写去重**（"Rock" 与 "rock" 视为同一标签）；长度 1–24 字符；不允许纯空白 |
| 重命名 | 冲突时提示"已存在同名标签，是否合并？" |
| 改颜色 | 从 8 色板选择，或"自动"（按创建序取色） |
| **改分类** | 标签页每行一个下拉（风格/社团/CV），改完立即同步专辑墙上方的分栏 |
| **合并** | A 合并到 B：A 的全部专辑关联迁移到 B，A 删除；冲突关联去重；操作前显示"将影响 N 张专辑" |
| 删除 | 仅解除关联，专辑不受影响；删除后 5 秒内 Toast 提供「撤销」 |
| 排序 | 默认按使用频次降序；支持手动置顶常用标签 |
| 批量打标 | 专辑墙多选 → 追加/移除标签（"追加"不覆盖已有标签） |

### 5.5.3 打标交互

```
专辑卡片悬停 → 🏷 → 弹出打标面板
  ┌──────────────────────────────┐
  │ 为「OK Computer」添加标签      │
  │ ┌──────────────────────────┐ │
  │ │ 输入标签名…            + │ │
  │ └──────────────────────────┘ │
  │ 已有标签：                    │
  │ [✓ 摇滚] [ 纯音乐] [ 日系流行] │
  │ [ 古典] [ 电子] [ 深夜循环]    │
  │ 最近使用：[氛围] [90年代]      │

  └──────────────────────────────┘
```

- 输入框实时过滤已有标签；无匹配时显示"创建『xxx』"；
- 点击标签即时切换选中态，底部显示"应用 (N)"；
- 应用后立即生效（纯库内操作，无需确认弹窗），Toast 提供撤销。

### 5.5.4 标签检索

| 方式 | 规格 |
| --- | --- |
| 标签筛选条 | 专辑墙顶部 chips；多选为 **AND** 语义（同时具备全部选中标签） |
| 高级筛选 | 标签下拉支持切换 **OR** 语义（具备任一标签） |
| 标签管理页 | 点标签 → 查看该标签下全部专辑 |
| 组合筛选 | 标签 + 关键词 + 音乐库 + 排序 可叠加 |
| 计数 | 每个标签显示专辑数；筛选条只显示 Top 20，"更多"展开全部 |

### 5.5.5 标签数据完整性

- 标签关联以 `album_id`（稳定 ID）为外键，**专辑元数据变化不影响标签**（这正是决定 1 的价值）；
- 专辑合并时：源专辑的标签迁移到目标专辑（并集去重）；
- 专辑被移除（库删除）时：`album_tags` 级联删除，标签自身保留（可能变成 0 专辑的标签，标记为"未使用"，可在标签管理页清理）。

### 5.5.6 可选：标签写回文件（默认关闭）

| 格式 | 映射位置 |
| --- | --- |
| MP3 / ID3v2 | `TXXX` 帧，描述符 `LAM:TAGS`，值以 `;` 连接 |
| FLAC / OGG / Opus | Vorbis comment `LAM_TAGS`（可多值） |
| MP4 / M4A | freeform atom `----:com.apple.iTunes:LAM_TAGS` |

**默认关闭的理由**：写入会污染文件、可能被其他软件误读，且标签属于"本软件的分类视角"。开启后需要用户明确知晓，并**同样走写操作安全框架**。

## 5.6 检索（R2 / R3）

### 5.6.1 关键词检索

| 项 | 规格 |
| --- | --- |
| 入口 | 顶栏全局搜索框（`/` 聚焦） |
| 匹配字段 | **曲名**、**艺术家**、专辑名、专辑艺术家、流派、年份、**标签名** |
| 匹配方式 | 大小写不敏感的子串匹配（`LIKE %kw%`，转义 `\ % _`） |
| 防抖 | 260ms（沿用 V1） |
| 结果 | 专辑墙过滤（专辑维度）+ 可切"曲目"结果列表；命中字段高亮 |
| 结果统计 | 顶栏显示"匹配 N 张专辑 / M 首曲目" |
| 空结果 | 明确提示 + "清除筛选"按钮 |

> **注意**：`LIKE` 对**音译/错字/拼音**无能力。拼音检索列为 V2.4 待定项（见第 11 章 Q4）。

### 5.6.2 标签检索

见 5.5.4。标签与关键词可组合，语义为 `(关键词匹配) AND (标签条件)`。

### 5.6.3 性能分级与升级路径

| 曲目规模 | 检索实现 | 预期响应 |
| --- | --- | --- |
| < 2 万 | 现状 `LIKE` 全表扫描 + 索引 | < 100 ms |
| ≥ 2 万 | **FTS5 虚拟表**（`title/artist/album/album_artist/genre/tag_names`）+ 触发器同步 + `LIKE` 兜底 | < 100 ms |
| 专辑墙渲染 | < 600 张全量渲染；≥ 600 张启用**虚拟滚动或分页**（V1 缺陷 D2 的修复） | 滚动 60fps |

阈值作为配置项（`config.json.search.ftsThreshold`），默认自动判定。

## 5.7 歌词（R4）

### 5.7.1 来源识别与优先级

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1 | **同名 `.lrc`** | `01 - Title.mp3` → `01 - Title.lrc` |
| 2 | **内嵌歌词** | ID3 `USLT`/`SYLT`、Vorbis `LYRICS`、MP4 `©lyr`（经 `music-metadata` 的 `common.lyrics` 读取，含同步歌词） |
| 3 | **模糊匹配的 `.lrc`** | 见 5.7.2 的二级匹配 |
| 4 | **整专辑共用 `.lrc`** | 目录内 `album.lrc` / 与专辑同名的 `.lrc` → 该专辑全部曲目共用 |
| 5 | **同名 `.txt`** | 无时间轴，静态展示 |

### 5.7.2 文件名匹配策略（三级）

| 级别 | 规则 | 例 |
| --- | --- | --- |
| L1 精确 | 同目录、同主文件名 | `Track.flac` ↔ `Track.lrc` |
| L2 去音轨号前缀 | 去掉开头的 `数字 + 分隔符` 后比对 | `01 - Title.mp3` ↔ `Title.lrc`、`01.lrc` |
| L3 相似度 | 主文件名归一化（转小写、去标点空格）后**编辑距离相似度 ≥ 0.8** | `01_Title (Live).mp3` ↔ `01 Title.lrc` |

匹配在**同目录内**进行，不做跨目录搜索。同一 `.lrc` 被多个曲目匹配到时，**按 L1 > L2 > L3 顺序分配给最匹配的一个**，其余不分配（避免一首歌词挂满整张专辑）。

**压缩包曲目走同一套阶梯**（`docs/压缩包支持设计.md` §5.4.1）：阶梯实现为纯函数 `matchLyricName()`，磁盘目录与包内成员目录共用，只是"目录里有哪些文件"的来源不同（`readdir` vs `archive_members` 清单）。此外还有 **L1v** 一级：`<完整音频文件名>.<歌词扩展名>`，用于实测常见的 `01.开场.mp3.vtt` 命名。包内字幕未预读时**现场解出该成员**（几十 KB），预读时随音频一并落盘。

### 5.7.3 编码嗅探与解析

**编码嗅探顺序**（Node 内置 full-ICU 的 `TextDecoder` 已可直接解码这些编码，无需额外依赖 —— 已实测）：

```
① BOM 检测（UTF-8 BOM / UTF-16 LE / UTF-16 BE）
② 严格 UTF-8 解码（fatal: true）成功 → UTF-8
③ GB18030（覆盖 GBK/GB2312）
④ Big5
⑤ Shift_JIS
⑥ 兜底 latin1（并提示"编码识别可能不准确"）
```

识别结果在歌词页显示（如"编码：GB18030"），并提供手动切换编码的入口（识别错误时可纠正）。

> **实测结论**：`new TextDecoder('gbk').decode(Buffer.from([0xD6,0xD0,0xCE,0xC4]))` → `"中文"`，`big5` / `shift_jis` 同样可用，ICU 为 full 版本。

**LRC 解析规则**

| 特性 | 支持 |
| --- | --- |
| 时间标签 | `[mm:ss]`、`[mm:ss.x]`、`[mm:ss.xx]`、`[mm:ss.xxx]`、`[mm:ss:xx]`（容错） |
| 一行多时间戳 | `[00:12.00][01:30.00]同一句歌词` → 生成两条记录 |
| 元信息标签 | `[ti:]` `[ar:]` `[al:]` `[by:]` `[offset:]` `[length:]` → 解析但不作为歌词行 |
| 偏移 | `[offset:±毫秒]` 全局应用（正值提前） |
| 翻译/双语 | 同一时间戳的多行 → 第一行为原文，其余行标记为译文（样式区分，不丢失） |
| 空行 | 合并连续空行 |
| 无时间轴 | 全部行作为静态文本列表 |

### 5.7.4 滚动展示

| 项 | 规格 |
| --- | --- |
| 位置 | 「正在播放」页右侧（V-7），亦可固定在播放器上方（可选紧凑模式） |
| 当前行 | 字号 +15%、白色、加粗、左侧强调色竖条 |
| 相邻行 | 灰色（上一行略深），逐级降低不透明度 |
| 滚动 | 每次切行 `scrollTo({ behavior:'smooth' })`，使当前行**垂直居中** |
| 点击跳转 | 点击任意行 → `audio.currentTime = 该行时间` |
| 手动滚动 | 用户滚动时**暂停自动跟随**，3 秒无滚动操作后恢复 |
| 无时间轴 | 静态文本，不滚动，无高亮 |
| 无歌词 | 占位："未找到歌词文件" + 「手动添加歌词」按钮 |
| 性能 | 仅渲染 ±50 行窗口（长歌词 ≤ 200 行可全量渲染） |

### 5.7.5 手动添加 / 关联歌词

| 操作 | 流程 |
| --- | --- |
| 关联已有文件 | 用文件选择框指定 `.lrc` → 记录 `track_id → lrc_path` 关联（存库） |
| 粘贴歌词 | 粘贴文本 → 保存为 `<同目录>/<同名>.lrc`（**新建文件，属写操作**，登记 write job 可撤销） |
| 修正编码 | 选择编码重新解析（只读操作） |

> 写 `.lrc` 不涉及替换音频文件，流程比 5.3.3 简单：备份同名已存在文件（若有）→ 直接写入 → 校验可解析。

## 5.8 播放（R5）

### 5.8.1 队列模型

沿用 V1 的**隐式队列**（触发播放的列表整体成为队列），并补充：

- 队列来源标记（专辑 / 全部曲目 / 搜索结果 / 标签筛选结果），在播放器 tooltip 显示"队列：专辑《OK Computer》· 12 首"；
- 队列为空时禁用播放控件；
- 显式队列面板与"下一首播放"列为 V2.4 待定（第 11 章 Q5）。

### 5.8.2 三种播放模式（精确定义）

| 模式 | 图标 | 一首播完 | 到达队尾 | 用户点「下一首」 | 用户点「上一首」 |
| --- | --- | --- | --- | --- | --- |
| **列表循环**（默认） | 🔁 | 播队列中下一首 | 回到队列第 1 首 | 下一首 | 历史栈上一首 |
| **单曲循环** | 🔂 | 重播本曲 | 重播本曲 | **仍切下一首**（主动切歌不受模式限制） | 历史栈上一首 |
| **随机播放** | 🔀 | 从洗牌序列取下一条 | 一轮播完后**重新洗牌** | 洗牌序列下一条 | 历史栈上一首 |

**随机的实现约定**

- 进入随机模式时对**当前队列**执行 Fisher-Yates 洗牌，生成 `randomOrder[]`，并把**当前曲目置于序列首位**；
- 用 `randomCursor` 顺序消费 `randomOrder`，**一轮内不重复**；
- 维护独立的 `history[]` 栈记录**实际播放过**的曲目，「上一首」出栈回退 —— 避免"上一首"变成随机跳转导致用户迷失；
- 单曲循环下点「上一首」若播放进度 > 3s → 先回到本曲开头（沿用 V1 行为）；
- 模式切换时**保持当前曲目与播放进度**；随机 → 其他模式时丢弃洗牌序列；
- 模式持久化在 `localStorage.playMode`。

**播放失败**：沿用 V1（Toast 提示文件可能已损坏或被移动），并**自动跳到下一首**（V1 是停住），避免队列卡死；连续 5 首失败则暂停并提示。

| 变化 | 规格 |

## 6.3 专辑重聚合规则（决定 1 的关键算法）

**触发时机**：① 写回后重新解析 ② 扫描时发现元数据变化 ③ 用户手工编辑专辑字段。

```
设：track 的专辑字段变化后算出 newKey

① newKey === album.album_key
   → 无事发生

② newKey 尚未被任何专辑占用（纯改名）
   → 更新 album.album_key = newKey，id 不变
   → 同步更新 title / album_artist / year
   ★ 标签、封面、豁免、id 全部延续 —— 这是"改名不丢分类"的核心

③ newKey 已被另一张专辑 target 占用（两专辑合并）
   → 把 track 的 album_id 指向 target.id
   → album_tags：源专辑的标签并集复制到 target（去重）
   → album_ignore：同样并集
   → 若 target 无封面而源专辑有 → 源封面迁移给 target
   → 若源专辑已无曲目 → 删除源专辑
   ★ 两张专辑的标签都不会丢

④ 专辑内多曲目批量改名时
   → 第一条触发 ② 或 ③，后续曲目算出相同 newKey → 走 ①
   ★ 行为一致，不会出现"部分合并"的中间态
```

**手工合并/拆分**（V2.3）：提供"合并到…"与"从专辑中移出"入口，直接操作 `album_id`，走同一套标签迁移逻辑。

## 6.4 迁移方案（V1 → V2）

迁移在**单个数据库事务**内完成，执行前自动复制 `library.db` 到 `data/backup/library.db.v1.bak`。

| 步骤 | 操作 |
| --- | --- |
| 1 | 读取 `meta.schema_version`；已是 2 则跳过 |
| 2 | 创建 `albums` / `tags` / `album_tags` / `album_ignore` / `write_jobs` / `write_job_items` / `meta` |
| 3 | 按 `album_key` 分组回填 `albums`（`title`/`album_artist`/`year`/`genre` 取自组内值，空值用展示占位） |
| 4 | `UPDATE tracks SET album_id = (SELECT id FROM albums WHERE album_key = tracks.album_key)` |
| 5 | 把 `covers` 表数据并入 `albums.cover_hash/cover_source`，然后 `DROP TABLE covers` |
| 6 | `ALTER TABLE libraries ADD COLUMN display_name`，按路径文件夹名回填 |
| 7 | `ALTER TABLE tracks ADD COLUMN album_id / meta_source / title_source / override_json / lyrics_path` |
| 8 | 建索引（`album_id`、`tags(name)`、`album_tags(tag_id)`） |
| 9 | 写入 `meta.schema_version = 2`，提交事务 |

**回滚**：迁移是单向的；回滚 = 停止服务 → 用 `data/backup/library.db.v1.bak` 覆盖 `library.db`。
**注意**：V2 新增的列不会影响 V1 代码运行（V1 只读它认识的列），因此降级时旧索引仍可用，只是丢失标签等 V2 数据。

## 6.5 存储布局与"用户资产"清单

```
data/
├─ library.db                  索引 + 用户资产
├─ covers/<sha1>.<ext>         封面缓存（内容寻址，可由源文件重建）
├─ undo/<jobId>/…              写操作备份          ← 不可重建
├─ backup/                     数据库快照 + 用户资产 JSON 导出 ← 不可重建
└─ config.json                 端口、阈值、保留策略
```

| 分类 | 内容 | 删掉会怎样 |
| --- | --- | --- |
| **可重建（索引）** | `tracks`、`albums` 的元数据、`covers/` 文件 | 重新扫描即恢复 |
| **不可重建（用户资产）** | 库别名、`tags`、`album_tags`、`album_ignore`、手动封面选择、`db-override` 值、歌词人工关联、写任务历史 | **永久丢失** |

因此：

- `GET /api/backup/export` 导出全部用户资产为单个 JSON（含版本号）；
- `POST /api/backup/import` 支持合并导入（按专辑聚合键/路径匹配，冲突时询问）；
- 自动备份：每次应用用户资产变更后（打标、建库），落一份 `data/backup/user-assets.json`（保留最近 10 份）；
- **歌词文件本身不复制**：自动匹配的歌词每次按需读盘（避免磁盘上出现两份歌词，导致用户改了 `.lrc` 却看到旧内容）；仅"手动关联"的关系存库。

# 8. 非功能需求

## 8.1 写操作安全（本版本的最高优先级）

| 要求 | 具体指标 |
| --- | --- |
| 原子性 | 任何单文件写入，原文件只会是"旧内容"或"新内容"，不存在中间态 |
| 备份完整性 | 备份未成功则**禁止写入**（硬性约束，不可配置关闭） |
| 互斥 | 同一时刻只允许一个写任务；写任务与扫描互斥 |
| 幂等 | 同一写任务重复执行结果一致（先比较当前值，无变化则跳过） |
| 可审计 | 每个受影响文件都有记录：路径、状态、错误、备份文件 |
| 可撤销 | `done` 与 `failed` 状态的任务均可撤销（撤销已成功的部分） |
| 中断恢复 | 进程被杀后重启：残留临时文件清理 + 任务标记 `interrupted` + 提示用户 |
| 乐观锁 | 编辑期间文件被外部修改 → 拒绝写入，绝不覆盖他人的改动 |

## 8.2 性能

| 场景 | 目标 |
| --- | --- |
| 写回单张专辑（12 首 MP3，约 100 MB） | ≤ 30 s（含备份、写入、校验、索引同步） |
| 写回并发度 | **默认串行（1）**，避免机械硬盘随机写抖动；SSD 上可配置为 2 |
| 待完善工作台加载 | ≤ 500 ms（走聚合查询 + 索引） |
| 标签筛选（1 万专辑、200 标签） | ≤ 200 ms |
| 歌词加载与解析 | ≤ 100 ms（含编码嗅探），内存 LRU 缓存最近 50 首 |
| 专辑墙（≥ 600 张） | 虚拟滚动或分页，滚动 60 fps |

## 8.3 可靠性与兼容

| 项 | 要求 |
| --- | --- |
| Windows 长路径 | 路径 > 240 字符时给出警告并提示启用长路径支持 |
| 文件被占用 | 跳过并报告，不阻塞整个任务 |
| 网络盘 / NAS | **不保证**写入可靠性（重命名与 replace 语义可能不一致）→ 启动检测到 UNC / 网络驱动器时给出警告 |
| 磁盘空间 | 写前检查剩余空间 ≥ 文件大小 × 2.2，不足则中止任务 |
| 依赖许可 | `node-taglib-sharp` 为 LGPL-2.1-or-later，需在 `THIRD-PARTY.md` 中登记 |
| 无原生模块 | 保持纯 JS 依赖（V1 的部署优势），不引入需要编译的包 |

## 8.4 安全边界

- 无鉴权（单机单用户）；`HOST` 改为 `0.0.0.0` 会让同网段任何人获得**写文件能力** —— 必须在 README 与设置界面显著警告；
- 上传/选择的封面图片：限制 ≤ 10 MB，按魔数校验真实格式，拒绝非图片；
- 所有文件路径来自数据库或用户显式输入，`path.resolve` 后校验必须位于已登记的音乐库目录内（防路径穿越）；
- 歌词与封面接口不接受任意远程 URL（保持本地优先）。

# 10. 迭代路线图

## 10.1 排序原则

1. **零风险的先做**：不写文件的需求（标签、歌词、播放模式、提醒、专辑墙）全部排在写操作之前；
2. **地基先于功能**：专辑实体化与用户资产导出是标签/封面/编辑的前置条件；
3. **测试先于写操作**：D4 未解决前不启动 V2.2；
4. 每个版本交付**可验证的验收标准**。

## 10.2 V2.1 —— 地基与只读增强（风险：低）

**目标**：在不碰用户任何文件的前提下，交付 R3、R4、R5、R6 与 R2 的"提醒"部分，并打好数据地基。

| 项 | 内容 | 来源 |
| --- | --- | --- |
| 专辑实体化 | `albums` 表 + `tracks.album_id` + 重聚合算法 + **V1 数据迁移** | D15 |
| 用户资产保护 | 导出/导入 JSON + 自动备份 + 界面区分"可重建/不可重建" | D16 |
| 完整性引擎 | 字段级别规则、合辑豁免、状态分级（含 D21） | R2 |
| 待完善工作台 | 分组视图 + 列表视图 + 豁免 + 忽略 | R2 |
| 标签体系 | 表结构 + CRUD + 合并 + 打标面板 + 标签管理页 | R3 |
| 标签检索 | 筛选条（AND）、下拉（OR）、与关键词组合 | R3 |
| 歌词 | 三级匹配 + 编码嗅探 + LRC 解析 + 滚动展示 + 正在播放页 | R4、D18 |

| 清理 | 移除 `lastError` 死字段 | D13 |

**验收标准**

- V1 的 `library.db` 能被自动迁移到 V2，**迁移前后专辑数、曲目数、封面显示完全一致**，且迁移前自动生成备份；
- 把一张专辑改名（模拟）后，它的标签、封面、豁免**全部保留**（重聚合测试覆盖改名与合并两条路径）；
- 专辑数 1200 时专辑墙可浏览全部，无静默截断；
- 5000 曲目库的关键词与标签检索 ≤ 200 ms；
- 一个 GBK 编码的 `.lrc` 能正确识别为 GB18030 并滚动展示；
- 三种播放模式行为符合 5.8.2 的逐格定义（含随机一轮不重复、上一首走历史栈）；
- `npm test` 全绿。

## 10.3 V2.2 —— 安全写回（风险：高）

**目标**：交付 R2 的写回能力，且让"改坏文件"在实践中不可能发生。

| 项 | 内容 |
| --- | --- |
| 写操作框架 | write job 状态机、备份、原子替换、校验、撤销、重试 |
| 写入器接入 | `node-taglib-sharp` 适配器 + 格式矩阵 + `node-id3` 降级 |
| 元数据编辑 | 编辑抽屉（单曲/专辑/批量）、空值语义、影响面预览 |
| 封面管理 | 添加/更换/移除、三种写入方式、多曲目一致性处理（D20） |
| 库重命名 | **仅显示名（PATCH），不触碰文件系统** |
| 降级路径 | `db-override` 标记与"未写回"全套 UI + 稍后重试 |
| 写任务 UI | 进度、逐文件结果、历史记录、撤销入口 |
| 安全加固 | 路径白名单校验、磁盘空间检查、长路径与网络盘警告 |

**验收标准**

- 批量写回 500 个文件后，**一键撤销能恢复到字节级相同**（抽样比对 SHA-1）；
- 强制在写入中途 kill 进程 → 原文件完好、临时文件被清理、任务标记 `interrupted`；
- 目标文件被其他程序占用时任务不中断，失败项精确列出并可在释放后重试；
- 编辑期间外部修改文件 → 拒绝写入并提示，**不覆盖外部改动**；
- 只读文件 / 不支持格式 → 自动降级为 `db-override`，界面明确显示"未写回"；
- 写操作相关的错误分支在测试中全部覆盖（占用、权限、磁盘满、校验失败、乐观锁冲突）。

# 13. 测试与发布流程（V1.0.0 新增）

## 13.1 分级测试原则

> **改哪里就测哪里；只有准备打包发布时，才跑完整流程。**

早期开发中每完成一项功能就新增一个 `roundN-check.mjs` 套件，导致大量重复断言（例如「侧栏有三个收藏入口」在三个套件里各验证一遍）。V1.0.0 对此做了整理：

- 按**功能区域**重组测试资产（`tools/check/`），区域之间断言不重复
- 提供统一运行器 `tools/check/run.mjs`，支持按改动自动选择区域
- 删除 11 条跨套件重复断言（190 → 179 条）

完整的区域清单、改动映射规则、命令速查见 [`docs/测试流程.md`](测试流程.md)。

## 13.3 测试数据纪律

1. 每个套件开头**重置自己关心的状态**，保证可重复运行
2. 测试写入的数据**必须还原**：先记原值，结束逐条写回（禁止「全部清空」式清理——历史上曾因此误删真实社团数据）
3. 单元测试**绝不触碰 `E:\Music`**，全部在 `os.tmpdir()` 临时目录内完成
4. 破坏性脚本（如 `tools/dev/scan-check.mjs` 会删除真实索引记录）**不纳入自动流程**

## 13.4 纯净发布

**问题**：开发期的库会积累测试专辑、测试标签、收藏记录与封面缓存。直接打包会把它们带给用户——用户第一次打开就看到一堆陌生专辑。

**做法**：`tools/release/build.mjs` 在打包后、临时目录里新建一个空库，校验 `albums / tracks / tags / libraries` 全为 0，再写入 `Release/data/`：

```
1. 前置检查（版本号、图标、Electron 运行时）
2. 完整测试流程（不通过则中止）
3. 清理上一版产物
4. electron-builder 打包便携版
5. 生成纯净数据目录（空库 + 空 covers/backup/undo）
6. 校验产物（大小、空库、schema_version）
```

便携版的数据位置由主进程 `resolveDataDir()` 决定：

1. 环境变量 `LAM_DATA_DIR`
2. `<exe 同级>/data/` 下**存在 `library.db`** → 便携模式，数据随 exe 走
3. 否则退回 `%APPDATA%\Luna\data`

发布包已带干净 `library.db`，因此便携版开箱即用且数据不外溢。

## 13.5 版本与提交规范

- **提交分组**：按子系统组织（脚手架 / 服务端 / 前端 / 桌面外壳 / 测试 / 文档），而非按时间堆叠
- **标签**：每次发布打 `v<major>.<minor>.<patch>` 标签
- **产物命名**：`Luna_v<major>.<minor>.exe`（便携版，单文件）
- **发布前必跑** `pnpm test:full`

## 13.6 V1.0.0 的已知限制

| 限制 | 说明 | 影响 |
| --- | --- | --- |
| 源图标仅 64×64 | `icon/Luna.png` 尺寸偏小，放大到 256 会偏软 | 大尺寸下图标不够锐利；16px 时花体字与波形不可辨 |
| 未实现 DSD/整轨镜像的转码播放 | 浏览器无法直接解码 DSD | 此类文件可入库但播放走代理时可能失败 |

| 台本仅在无字幕时启用 | 同目录存在字幕文件时优先字幕 | 无法手动在字幕/台本之间切换 |

# 附录 B｜LRC 格式规范摘要

```
[ti:曲名] [ar:艺术家] [al:专辑] [by:制作人] [offset:+500]   ← 元信息，不作为歌词行
[00:12.00]第一行歌词
[00:15.30][01:20.50]同一句歌词出现在两个时间点      ← 一行多时间戳 → 生成两条
[00:18.00]原文
[00:18.00]译文                                        ← 同时间戳 → 第二行标记为译文
```

| 记号 | 含义 |
| --- | --- |
| `[mm:ss]` `[mm:ss.x]` `[mm:ss.xx]` `[mm:ss.xxx]` | 分钟:秒[.毫秒]，毫秒位数不固定 |
| `[offset:±ms]` | 全局时间偏移，正值表示歌词提前显示 |
| 无时间标签的行 | 纯文本歌词（静态展示，不滚动） |
| 编码 | 常见 UTF-8 / GBK / GB18030 / Big5 / Shift_JIS，需嗅探（5.7.3） |

| 歌词 | 无 | 三级匹配 + 编码嗅探 + 滚动展示 |
| 播放模式 | 单曲循环开关 | 列表循环 / 单曲循环 / 随机（三态） |
| 完整性 | 缺失即显示"未知" | 主动检测、分级提醒、工作台批量完善 |
| 音乐库 | 路径 | 路径 + 显示名（别名），不触碰文件系统 |
| 依赖 | express + music-metadata | + `node-taglib-sharp`（纯 JS，LGPL-2.1） |
| 风险等级 | 极低 | 高（写文件）→ 由安全框架、测试与备份兜底 |

# 13. 测试与发布流程（V1.0.0 新增）

## 13.1 分级测试原则

> **改哪里就测哪里；只有准备打包发布时，才跑完整流程。**

早期开发中每完成一项功能就新增一个 `roundN-check.mjs` 套件，导致大量重复断言（例如「侧栏有三个收藏入口」在三个套件里各验证一遍）。V1.0.0 对此做了整理：

- 按**功能区域**重组测试资产（`tools/check/`），区域之间断言不重复
- 提供统一运行器 `tools/check/run.mjs`，支持按改动自动选择区域
- 删除 11 条跨套件重复断言（190 → 179 条）

完整的区域清单、改动映射规则、命令速查见 [`docs/测试流程.md`](测试流程.md)。

## 13.3 测试数据纪律

1. 每个套件开头**重置自己关心的状态**，保证可重复运行
2. 测试写入的数据**必须还原**：先记原值，结束逐条写回（禁止「全部清空」式清理——历史上曾因此误删真实社团数据）
3. 单元测试**绝不触碰 `E:\Music`**，全部在 `os.tmpdir()` 临时目录内完成
4. 破坏性脚本（如 `tools/dev/scan-check.mjs` 会删除真实索引记录）**不纳入自动流程**

## 13.4 纯净发布

**问题**：开发期的库会积累测试专辑、测试标签、收藏记录与封面缓存。直接打包会把它们带给用户——用户第一次打开就看到一堆陌生专辑。

**做法**：`tools/release/build.mjs` 在打包后、临时目录里新建一个空库，校验 `albums / tracks / tags / libraries` 全为 0，再写入 `Release/data/`：

```
1. 前置检查（版本号、图标、Electron 运行时）
2. 完整测试流程（不通过则中止）
3. 清理上一版产物
4. electron-builder 打包便携版
5. 生成纯净数据目录（空库 + 空 covers/backup/undo）
6. 校验产物（大小、空库、schema_version）
```

便携版的数据位置由主进程 `resolveDataDir()` 决定：

1. 环境变量 `LAM_DATA_DIR`
2. `<exe 同级>/data/` 下**存在 `library.db`** → 便携模式，数据随 exe 走
3. 否则退回 `%APPDATA%\Luna\data`

发布包已带干净 `library.db`，因此便携版开箱即用且数据不外溢。

## 13.5 版本与提交规范

- **提交分组**：按子系统组织（脚手架 / 服务端 / 前端 / 桌面外壳 / 测试 / 文档），而非按时间堆叠
- **标签**：每次发布打 `v<major>.<minor>.<patch>` 标签
- **产物命名**：`Luna_v<major>.<minor>.exe`（便携版，单文件）
- **发布前必跑** `pnpm test:full`

## 13.6 V1.0.0 的已知限制

| 限制 | 说明 | 影响 |
| --- | --- | --- |
| 源图标仅 64×64 | `icon/Luna.png` 尺寸偏小，放大到 256 会偏软 | 大尺寸下图标不够锐利；16px 时花体字与波形不可辨 |
| 未实现 DSD/整轨镜像的转码播放 | 浏览器无法直接解码 DSD | 此类文件可入库但播放走代理时可能失败 |
| 视频版不参与音频队列 | `.mp4` 作为独立「视频版」按钮弹窗播放 | 顺序播放时会跳过视频 |
| 台本仅在无字幕时启用 | 同目录存在字幕文件时优先字幕 | 无法手动在字幕/台本之间切换 |
